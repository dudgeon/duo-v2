Duo v2 code review · 8 November 2026

Duo's hidden state machines

Much of Duo's state lives in loose flags, spread across the code. This page explains what that means, why it causes the bugs you've been seeing, and what to do about it.

The short version

  • I found 24 of these hidden machines. Six are worth real work. The rest want a small change or none.
  • The biggest: a session has no single state. At least nine places in the code decide what state a session is in, and they disagree at the edges. About 36 logged incidents live there.
  • The most patched: chat or terminal? That has been fixed at least nine times, mostly by adding another timer.
  • The cure already works here. Three data-loss bugs in the editor became one explicit machine (F-264), and that fault hasn't come back.
  • Reading the code turned up 20 likely bugs. One you can probably reproduce today: click Earlier turns on a long chat, and newer turns vanish. None of the 20 has been run yet.

Recommendation: three steps, about two weeks of sessions. Small fixes first, then one answer to "what state is this session in?", then chat. Nothing needs deciding today.

The fundamentals

A state and a transition

A state is the situation something is in right now. A transition is a move from one state to another, caused by an event.

A state machine is the full list of both. It says what situations exist, and which moves are allowed. Any move not on the list can't happen.

That is an explicit state machine. Someone wrote it down in one place, and you can read it. Its logic is 18 lines of Duo's code.

Implicit: the same thing, unwritten

Software always has states. A terminal tab really is running, or closing, or gone. The question is whether anyone wrote that down.

An implicit state machine is one nobody wrote down. The state is scattered across true-or-false flags and blank-or-filled fields, and the rules live in the heads of whoever wrote each line. Here is a real one, a terminal tab in Duo. Press the flags.

RunningThe process is alive.

4 flags make 2 × 2 × 2 × 2 = 16 combinations. 6 of them mean something.

Why flags make more states than anyone intends

Each new flag doubles the combinations. Two flags make 4, six make 64, ten make 1,024. The real situations grow slowly, and the combinations grow fast.

An impossible state is a combination that means nothing but can still occur. The computer doesn't object. Each part of the app reads the flag it cares about and acts on it, so one part thinks the session is closed while another thinks it's running.

In Duo today, a tab can be both closed and parked. Press ⌘W on a restored tab: the process ends, but the parked mark stays. So the tab stays too.

A race is a missing transition

"Race" and "stale callback" sound like bad luck. They're mostly a gap in the list of states.

Duo often asks for something and gets the reply later: read this file, get the editor's text. Meanwhile, you've moved on. The reply arrives into a situation it wasn't asked for. A stale callback is that late reply, acting as if nothing had changed.

If the state machine had listed that situation, it would say what to do. Usually: drop the reply. Duo's fix for this is a generation token, which works like a deli counter ticket. Each document on screen gets a new number, and a reply holding an old number is ignored.

A timer standing in for a state

Duo's code has 89 timers. Some are right: Claude Code's screen gives no signal that it has finished drawing, so waiting a moment is the only honest option.

Many others guess how long something takes, because the state "waiting for that" has no name and no event ends it.

A guess that's right on your Mac can be wrong on the work Mac, under load, or after an update. So these bugs come and go, and they're hard to reproduce.

Why it gets worse by itself

A bug caused by flags gets fixed by adding a flag or a timer. It's the smallest change that works, so it's a sensible choice each time. But each one doubles the combinations again, and the next person has more to keep in their head.

The log shows this repeating: rowHold and localChange (F-135), a 15 s grace over a 1.5 s grace (F-419), queuedCollapse then minimumOverrides then a 0.35 s wait (F-527, F-532, F-501). And Sonnet sessions make these fixes without the history in their heads, which makes the rules that live only in someone's head especially costly here.

What making it explicit buys, and costs

Making it explicit means three things: one list of states, in place of the flags (an enum, a value that can only be one thing from a list); one function that takes a state and an event and returns the next state; and one check for each arrow.

What it buysWhat it costs
Impossible states can't be written. The code won't compile.More code up front, and every new state needs a decision. A quick fix gets a little slower.
A late reply or odd event meets a defined answer: usually, ignore it.A refactor can break what works. Chat's flags encode many small hard-won lessons, and each has to carry across.
The next Sonnet session reads the rules in one place.Where AppKit, WebKit or Claude Code owns the truth, an enum only mirrors it. So some machines should stay as they are.
You get better product questions. "What happens if this arrives while that's up?" becomes a visible empty cell.It doesn't make the outside world tidy. Claude Code's screens can still surprise Duo, but "I can't read this" becomes a named state.

Testing a machine made of flags

  • Launch the app, drive a real case, read the bytes on disk.
  • Each case takes seconds and needs a whole app.
  • You find the case after the bug: F-263 became a case once it had lost someone's typing.
  • The editor's host check does this well, with 19 assertions when F-264 wrote it. DuoChecks has none for it.

Testing an explicit machine

  • Call one function: state in, event in, state out.
  • No app, no microphone, milliseconds.
  • One case per cell, so the count is known. Dictation's whole table is 9 states by 12 events.
  • You still want a few live runs, to prove the real world behaves as the table assumes.

A worked example: how Duo lost your typing

F-263 is a real incident. You're typing in document A, Claude writes to that same file, and you switch to B within about 150 ms. Your typing was gone, silently.

The check at step 5 was self.url == file: "is this reply about the document on screen?" It seems reasonable, and it failed in both directions. It bailed when it shouldn't have. And it couldn't tell A from "A again, after B", so a stale reply could pass as a fresh one.

This wasn't a one-off. F-264 records that F-44, F-52 and F-263 were one fault: three bugs in six days, including a save written against the wrong file's bytes and a lost last word on quit. Each had been fixed where it showed. The fix that ended the class replaced two loose flags with one enum (closed, opening, open, conflict, removed) and added the ticket. I found no recurrence of that fault in the log since.

That's the case for doing this elsewhere. It has already worked in Duo, on the bug class that matters most.

The six serious ones

Each has the same picture twice. On the left is the machine as it is: the flags, how many places write them (the × number), and the files that hold those writes. On the right is the same machine drawn as states and arrows. Those are my inference, for discussion, and they aren't a design. The chips rate the cost to you (what you see), to building (how hard it is to change and test) and to structure (what else it tangles).

Session life

Make explicitYou: highBuilding: highStructure: high

What state is this session in? It sounds like one question. Duo answers it in at least nine places.

What goes wrong. Press ⌘W on a tab restored at launch. Its process ends, but the tab stays and comes back as parked. The tab's own Close button does remove it. That's because only one of the two close paths clears the parked mark. Use /clear and Keep Running is silently lost, because the pin is filed under the old id and nothing moves it. About 36 entries in the findings log live here, the most of any area (F-126, F-208, F-210, F-360, F-405).

Why it's hard to change. tabSessions decides a tab exists from an OR of four things minus a fifth. There are two hand-kept lists of what to move when a session's id changes, and they differ. Views get told to redraw by fixture = fixture, a line that assigns a value to itself.

Recommendation. Add a read-only SessionLife computed from today's stores, and move the readers onto it one at a time. Nothing changes for you on day one. Then give parked one writer, and give rekeying one function. ENH-333, C-171.

A terminal tab's process

Make explicitYou: mediumBuilding: mediumStructure: high

One tab's real process, from start to reaped.

What goes wrong. exited is true while the process is still alive, from the moment Duo signals it until it's reaped. Readers that ask "is it running?" get no for a live process. In F-126, three sessions sat half-exited, archive refused them, and a second close said "isn't running in Duo".

Recommendation. One TerminalLife enum replaces the flags, and Session life reads it. ENH-333.

The chat surface

Make explicitYou: highBuilding: highStructure: medium

Does this session show chat, or the terminal, and when does it come back?

What goes wrong. This has been patched more often than anything else: F-105, F-108, F-173, F-208, F-243, F-376, F-419, F-437 and F-449. Most fixes added a timer. F-419 is the shape of it. A 1.5 s grace timer fired before the feed had read Claude's request, so you got "Can't match this dialog". The fix added a second grace, of up to 15 s. Q-257 and Q-328 are the same machine, asked as product questions.

What's already good. Every fallback goes through one door, fallBack, with a named rule and a log line. Keep that. evaluateFallback is nearly a transition function already, so this is a shorter step than it looks.

Recommendation. Make it pure: state, event and clock go in, and state and effects come out. ENH-334, first slice.

The prompt channel

Make explicitYou: highBuilding: highStructure: medium

Send, carry, answer, paste, the / mirror and peek all type into one real prompt. Who has it now?

What goes wrong. F-452: a dictated passage reached Claude about three times, and Return and Esc went dead. F-485: typed words were left behind. Two more read from the code. send has no "already sending" guard, although its siblings do, so a second Return during a send may type twice. And if you return to chat during a carry, it still finishes and empties the composer, and nothing fills it until the next toggle.

Recommendation. One owner of the prompt: a queue with one job at a time. The / mirror's one-at-a-time loop (F-420) is the pattern to grow from. ENH-334, second slice, C-172.

The editor document

TightenYou: highBuilding: mediumStructure: medium

A document from opening to closed, across saves, Claude's edits and conflicts. This one is half built.

Did DL-167 step 5 happen? Half. The enum and the generation token exist, and they worked: the fault behind F-44, F-52 and F-263 hasn't come back. What's missing is the cheap part. phase has 14 assignments with no single place that says which moves are legal. And no DuoChecks case tests a transition. The proof is check-editor-host.sh, which launches the app once per case.

What goes wrong now. A document remembered in Source mode opens in preview on launch, because the page is told the mode list after it shows the first document. A keystroke in a few-millisecond window can count as saved.

Recommendation. One private move(to:), fold the side fields in, and add a check on a fake page with no web view. Medium.

Split room and the pane slide

TightenYou: mediumBuilding: highStructure: medium

Opening a split takes room from the console and sidebar. Closing it should give back exactly that.

What goes wrong. F-9, F-130, F-501, F-527, F-531 and F-532 are all this machine. A closed split left the sidebar hidden. A restored split came back folded with room to spare. Each fix added a delay or a flag.

Recommendation. Make the room one enum, and replace the 0.35 s wait with the slide's end. Do it the next time this area is touched. The pure parts (SplitRoom.plan, PaneWidths.resized) are good and stay.

What's already good

Some of Duo is already explicit, and it's the model for the rest. Leave these alone.

Real machines

  • VoiceMachine: dictation's states, tested with no microphone.
  • Migrator: a journal saved at each step, so a crash can be undone.
  • ParkCheck: an ordered list of reasons a tab can't park.
  • gpu-lock.sh: a written protocol with its own check. It took four rounds to earn that (F-294, F-296, F-298, F-510).

State that can't disagree, because it's derived

  • Suggest Edits: a line in the file itself.
  • RepoStatus: read fresh from git, never remembered.
  • The search index's "complete": computed from a table.
  • showsChat: computed from two values, never stored.
  • fallBack: one door, and a log of who came through it.

The plan

Three steps, in this order. These are recommendations, and the decisions are yours once you've read this.

1

Fix the small ones small · about 2 days ENH-332

The nine bugs above, each with a failing check first, then the others as they're passed.

Why first: you see the difference at once, the risk is small and it needs no design. It also builds the kind of check that the next two steps lean on.

2

One answer to "what state is this session in?" medium · 3 to 4 days ENH-333

One enum for the terminal's process. One read-only SessionLife, with the nine readers moved onto it one at a time. One writer for parked, and one function for an id change.

Why second: the most incidents, and everything reads it. It starts read-only, so it can land with no change you'd notice. It also comes before anything else grows on top.

3

Chat: the surface, then the prompt medium to large · about 5 days ENH-334

First, make "chat or terminal?" a pure function with a test clock. Then, one owner of Claude's prompt, with one job at a time.

Why third: the most repeatedly patched, and every chat user feels it. It's also the riskiest, because it sits on Claude Code's screens. It's safer once the session underneath holds still.

Then, when each area is next touched: finish the editor (medium). Split room on events in place of the 0.35 s wait (medium). One overlay value (small to medium). A right-pane enum (medium). Route dictation through its machine (small).

A house rule to consider: two flags on one object that constrain each other become an enum, and a new timer's comment names the event it stands in for. It's small, and it stops the list growing.

What I'd avoid: a state-machine library or framework, or a rewrite in one go. And timers stay where Claude Code gives no event, though they should become named states.

What I couldn't confirm

  • Nothing was run. This review only read code. Severity is judgement, and a real run may find a guard I missed.
  • Two claims from the first sweep were wrong and I dropped them after re-reading the code.
  • Dictation across a document switch. It might land words in the wrong document, but I didn't read the code that routes them.
  • A few smaller claims rest on a subagent's reading, not mine. They're listed in the Markdown record.
  • The state diagrams are my inference from the code. They're for discussion, and they aren't a design or a decision.
