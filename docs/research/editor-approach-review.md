# Duo editor approach review

**Status:** research / decision input. Written 2026-10-09 by the editor review session for Geoff and the director. Also published as the Claude Doc "Duo editor approach review" (https://claude.ai/code/artifact/88b2ff9d-3cf2-491e-a0d7-9bdcb98fd3a5).
**Question (Geoff, 2026-10-09):** "Generally I find the markdown editor in v2 to be buggier than legacy; perhaps recent bug fixes squashed some of this, but I am not sure we have the right markdown renderer/editor approach." Is v2's approach right? If not, what replaces it and at what cost? If it is, what makes it feel buggy and what fixes that?
**Scope:** research and judgement only. No app code changed; no decision recorded (DL-n entries are Geoff's).

## Recommendation

**Keep the CodeMirror 6 live-preview editor. Do not switch engines.** It is the right approach for what Duo's editor is for: files that Claude, git, iCloud and Obsidian also write, which must come back byte for byte and merge without losing either side. That goal holds today by construction and by test (2,593 real files round-trip identical; zero round-trip bugs in seven days, against 26 of legacy's 49 editor bugs in that class, two still open at its last commit), and every comparable app that lives beside a vault or a sync client made the same choice. What makes v2 feel buggier than legacy is not the engine but five bounded classes, three of them visible to Geoff: block widgets whose CSS margins CodeMirror's height map cannot see, so clicks land lines away (C-25, F-251, and three more widgets proven today); the caret line changing height when it reveals its markdown; undo, caret and scroll lost on every tab switch; task-note YAML edits written twice, in JavaScript and in Swift; and a save path split between Swift and JavaScript whose async halves race on a document switch (F-263, merged today). Each has a small root fix and a check that keeps it closed, about two weeks of Sonnet sessions in total, before any new editor feature. Switching would cost four to eight weeks for a ProseMirror editor that brings legacy's serialiser bugs back, or three to five months for a native one that has no table primitive and failed the size spike. Geoff's decisions are the six questions at the end; the first is whether a stable-height editor may depart from the approved screens' 10 px blank lines.

## What the editor is for

Duo's editor is not a writing app. It is the place where a person reads and corrects documents that Claude, git, iCloud and Obsidian also write, inside a project. Seven goals follow from the decisions and the v1 test ("Geoff can use Duo all day instead of Terminal plus legacy Duo", build plan §3a). Ranked, highest first; a lower goal never buys a breach of a higher one.

| Rank | Goal | What it means | Where it comes from |
|---|---|---|---|
| 1 | Never lose or rewrite a word | Saves are byte-faithful: untouched text comes back byte for byte. Outside changes (Claude, git, iCloud) merge three-way without losing either side. Never two writers. | LR-30, LR-31, LR-32, DL-77, legacy's BUG-085 to BUG-166 arc |
| 2 | Files stay plain and portable | Every file Duo writes opens the same in Obsidian, GitHub and OKF tools: markdown links, no wikilinks written, no Duo dialect, tables one line per row. | DL-6, DL-17, DL-20, DL-113 guard, DL-152, the Obsidian/OKF rule |
| 3 | Claude's edits land in the editor, visibly | Edit, MultiEdit and Write to an open file go through the buffer, highlighted "added by Claude", revertable, merged with unsaved typing. The editor is the review surface for an agent's writing. | DL-5, DL-78, LR-33, LR-34, ENH-4 |
| 4 | Structured notes have a structured surface | Frontmatter is a properties block; a task note has status, sessions, references and a fields row; templates preview. The editor is the task editor. | DL-60, DL-102, DL-146, DL-150, LR-37 |
| 5 | Edit the rendered document, natively | No split view. Geoff's four criteria: native menus and chords, macOS spellcheck, dictation and Writing Tools, native-looking selection, caret, scroll and find, byte-faithful saves. Built to the screens (S3-5, DL-101). | stack-recommendation §Geoff's answers, DL-34, DL-79, DL-108, DL-26 |
| 6 | A conduit to Claude | Send Selection (⌘D), session links, `duo2 doc` verbs for every action. | DL-67, DL-79, DL-87, DL-71 |
| 7 | Cheap to build and run | Xcode-free, one web view, small bundle, no paid tier, fixes that a Sonnet session can make in a day. | DL-30, DL-153, stack research §4.3 |

Goals 1 to 3 are structural: breaching them loses data or trust, and legacy spent most of a year on goal 1 alone. Goals 4 to 6 are features. Goal 5 is where "feels buggy" lives, which is why it is felt most and matters least to the choice of engine: an engine that wins goal 5 and loses goal 1 is the legacy mistake again.

## Why v2 chose CodeMirror 6, and what it is today

The choice was made on 2026-10-03 from one lesson: legacy's editor held a ProseMirror document and re-serialised it to markdown on every save, and that step cost about a year of fixes (the BUG-085 to BUG-166 arc). The stack research (`docs/research/stack-editor-and-webview.md` §0, §4.2) found only two architectures that give byte-faithful saves cheaply: text-is-truth editors that decorate the text (CodeMirror 6 live preview, Bear, iA Writer), or a document-model editor with a lossless concrete-syntax round trip, which no ProseMirror or Lexical stack provides. The recommendation (stack §8, §9) was CodeMirror 6 live preview in one WKWebView, with a native TextKit 2 editor as a tracked successor and `swift-markdown-engine` as a hedge spike. Spikes S4 and S5 passed headless (F-34); the native hedge failed on size (F-39: 244 ms per keystroke on a 1.2 MB file).

What was built, in six days:

| Part | Where | Size today | Grew from |
|---|---|---|---|
| The editor module: live preview, properties block, task-note fields, Claude highlight and revert, tables, images, find, three-way merge, agent edits, Format commands | `Vendor/codemirror/src/duo-editor.js` | 2,342 lines, 26 commits | 290 lines on 2026-10-03 |
| The Swift host: one shared WKWebView, file watching, atomic saves, reconcile, conflict and removed-on-disk states, templates, menus | `Sources/DuoKit/Editor/DocumentEditor.swift` | 679 lines, 24 commits (F-263 merged during this review) | 179 lines on 2026-10-03 |
| CodeMirror 6 and Lezer markdown, bundled by esbuild | `Vendor/codemirror/dist/cm6.js` | 634 KB minified, 8 MIT packages | pinned 2026-10-03 |

How it works, in one paragraph. The file's text is the CodeMirror document. A view plugin walks the visible syntax tree and hides or replaces syntax with decorations (heading marks, emphasis marks, list bullets, checkboxes, rules, code fences, link brackets); the line holding each selection's anchor shows raw markdown instead. Tables and images are block widgets that swap to source when the caret is on their lines. The frontmatter is decorated in place as the properties block, so a property edit is a text edit and undo is the document's undo. Saves write `doc.toString()` with the file's own line separator, atomically, only when the bytes differ. An outside write is merged three-way by line (base, buffer, disk); non-overlapping hunks apply as one transaction and carets map through; an overlap pauses autosave and asks. Claude's Edit, MultiEdit and Write calls arrive through a hook and land as the same kind of transaction, highlighted and revertable.

Three facts about the build that matter for the judgement below:

- **Text is the only truth, everywhere.** Nothing in the module rewrites text the user did not act on; the properties block, tables and the title-follows-heading rule all edit lines surgically. Goal 1 holds by construction.
- **One CodeMirror instance, recreated per document.** `create()` destroys the view and builds a fresh state when a tab is shown, so undo history, caret, scroll position and folds do not survive switching tabs (only unsaved text in conflict is kept). The stack research proposed keeping per-document state (§7.3); it was not built.
- **Reveal is by line, and the design is compact.** A blank line is 10 px until the caret reaches it, then 20 px; a table is a widget until the caret enters it, then its source. Every reveal changes the height of the text above and below the caret, which is where C-25's "selection landed lines away" came from. This is a design tension, not an engine fault, and it recurs below.

The counts are not like for like: v2 is seven days and 517 commits old, legacy ran 151 days, 1,133 commits and 68 releases. Read the root-cause column, not the totals.

Two things the records do not hold. Geoff's walk verdicts are not in the repo (both ledgers say "Not yet read back"; they live in the walk page's `verdicts` collection, which only the director can read). And nothing has been run in WebKit itself: every scripted editor check runs in headless Chromium, and the Swift host (save, reconcile, watch, quit flush), the properties block, the table commands and the `duo2 doc` verbs have no automated test at all.

What legacy's editor had that v2 lacks today, with the record that wants it:

- Never showing syntax: typing `# `, `- [ ] ` or `**x**` converted in place (Stage 11 D2 rejected Obsidian-style reveal outright). v2 shows the caret line raw; the walk card `ed-format` asks whether that should be calmer.
- Paste or drop an image, saved beside the note (legacy FOLLOWUP-014, ENH-128 HEIC): LR-39 is in v1 scope and unbuilt.
- Wikilink and `@` autocompletion with `[[`: decided (DL-17, DL-152), not built (F-202).
- Inline comments and suggesting mode with accept and reject (CriticMarkup): deferred (DL-5, Q-62), and legacy's own version lost data four ways before it was fixed.
- A history browser with diff and restore (legacy ENH-221): v2 keeps snapshots and has no view.
- A line-number gutter matching what Claude's Read reports (legacy BUG-186).

## How comparable apps do it

Every editor that lives beside a vault, git or a sync client keeps the file as the truth and decorates it. Every editor that holds a document model and writes markdown out has a years-long trail of "don't touch lines I didn't edit" issues, some still open. Pages opened on 2026-10-09; the full list is in Sources.

| App or library | Engine | What is the truth | Outside changes | Known fidelity trouble |
|---|---|---|---|---|
| [Obsidian](https://docs.obsidian.md/Plugins/Editor/Editor+extensions) | CodeMirror 6 live preview; Source and Reading modes | The markdown file; syntax hidden, shown when the cursor enters it | Merges a note changed on disk with unsaved edits (0.11.6); users call it "really unreliable"; a 2026 report says a Claude Code edit did not show until the note was reopened | Tables became editable widgets only in 1.5.3 (Dec 2021 to Feb 2024), then auto-formatted on typing; users report "lines shift and the cursor jumps" when syntax toggles |
| [Zettlr](https://www.zettlr.com/post/zettlr-400-released) | CodeMirror 6 since 3.0 (14 months of migration) | The file | Removed a spurious "replace file?" prompt from cloud sync; fixed cursor jumps on external change in 3.0.3 | Its visual table editor was "brittle and essentially unfixable" and lost data; replaced in 4.0 after 18 months, with a Save button added because the flow from widget to markdown could not be controlled |
| [iA Writer](https://ia.net/writer/support/editor/syntax-highlight) | Native text view with syntax styling; preview is a separate view | The file; highlighting "does not modify your content in any way" | iCloud conflicts: pick a version | None found: it never renders in place |
| [Lettera](https://christiantietze.de/portfolio/lettera/) (Bear's team, beta June 2026) | Swift, AppKit, TextKit 1 ("never 2!") | "The file is the truth"; built to survive "sync clients rewriting bytes underneath you" | Designed in | Panda beta users lost text after adding an image, and table paste broke |
| [Typora](https://support.typora.io/Markdown-Export) | Closed, its own engine; a parse-and-write model | An internal model; "details that do not affect the final markdown representation will not be kept" | Not documented | Tables reformatted on save (#1189, 2018, still reported 2023); link definitions rewritten silently (#5229); blank lines inserted into lists (#5228, open) |
| [MarkText](https://github.com/marktext/marktext/issues/2189) (Muya) | Block tree, marked in, turndown out | Muya's JSON | Not documented | Files marked modified on open; lists renumbered, footnotes moved (#2189, open since 2020); "a one-line change produces diffs across the whole document"; Muya archived 2026-05 |
| [Milkdown](https://github.com/Milkdown/milkdown/issues/2349) | ProseMirror plus remark | The ProseMirror document | A change from outside is a full `replaceAll`, which loses the cursor and froze a large document (#2396) | Backslashes double on every round trip (#2349, 2026-04); no viewport virtualisation |
| [Tiptap markdown](https://tiptap.dev/docs/resources/changelog/markdown) (legacy's family) | ProseMirror plus MarkedJS, "early release" | The ProseMirror document | Same as Milkdown | A changelog of round-trip fixes: blank lines absorbed, `<` `>` `&` re-encoded, mixed task and bullet lists split. GitLab's rich editor still rewrites `a*b*c` to `a_b_c` with no edits (issue 628280, 2026-09) |
| [Lexical](https://lexical.dev/docs/packages/lexical-markdown), [BlockNote](https://www.blocknotejs.org/docs/foundations/supported-formats) | Lexical or ProseMirror document models | JSON; BlockNote: "converting to and from Markdown is a lossy conversion" | Document replace | Not built for files |
| [TextKit 2](https://developer.apple.com/videos/play/wwdc2022/10090/) native | Apple's text layout | Text storage | Up to the app | No table attribute (a one-way fallback to TextKit 1); developers report correctness and performance issues Apple has not answered; `swift-markdown-engine` is pre-1.0 and lays out whole documents without virtualisation |

Three things the field says about Duo's position:

- **Duo is in the Obsidian and Zettlr camp, and shares their problems.** CodeMirror 6 live preview has three structural costs, and Duo has met all three: caret and selection against hidden ranges, height-map drift from widgets and line-height changes, and block widgets that become a second editor. Obsidian lives with the first two; Zettlr spent 18 months on the third; DL-113 sidestepped it by editing tables as markdown with commands.
- **The ProseMirror camp's problem is the one Duo cannot afford.** Nobody ships a lossless concrete-syntax round trip. GitLab has been building a "preserve unchanged markdown" layer inside its serialiser since 2022 and has not finished. Milkdown's doubling backslashes are from April 2026. These are the legacy classes 1, 2 and 7, back.
- **Native is where the best-funded team went, on TextKit 1, in 2026.** Lettera confirms the text-is-truth model and the cost: a multi-year engine by a team, not a successor Duo can adopt. The 2026-10-03 spike (F-39: 244 ms per keystroke, 543 MB on the 1.2 MB file) stands.

The engine itself is healthy: CodeMirror's development moved to code.haverbeke.berlin on 2026-04-15, and npm releases continue (@codemirror/view 6.43.14 on 2026-10-07; Duo pins 6.43.13 of 2026-09-22).

## Options

Five options, judged against the ranked goals. Option 1 is the only one that keeps goals 1 to 3 and costs days rather than months. Options 2 and 5 are modes of option 1, not new engines, and two of them are nearly free because the module already has the switch (`duoFlags.noPreview` turns the live preview off).

| Option | Goals 1 to 3: byte fidelity, concurrent disk edits, Claude's edits | Goal 5: rendered, native feel | Obsidian and OKF compatibility | Bug classes removed / added | Migration cost | Risk |
|---|---|---|---|---|---|---|
| 1. Keep CodeMirror 6 live preview; fix the classes at their roots | Held today by construction and by test (2,593 files byte-identical; three-way merge; Edit-shaped transactions) | Obsidian's standard; the caret line shows raw markdown; spellcheck, dictation and Writing Tools through the editable DOM | Same engine and model as Obsidian; files untouched | Removes: decoration geometry (a widget rule plus a check with every widget), per-document state loss, twice-written YAML, chord arbitration by hand. Adds none | 8 to 12 session-days, listed below | Low. CodeMirror is maintained; the classes are bounded and each fix is small |
| 2. Same engine, a different rendering layer: (a) a Source mode per document, as Obsidian has; (b) a split source and preview | Unchanged | (a) a plain-text escape hatch when the preview misbehaves; (b) fails Geoff's "no split view" | Unchanged | (a) removes nothing, gives a fallback; (b) removes classes 3 and 4 and loses rendered editing | (a) half a day (the flag exists); (b) 2 to 3 days | (a) none; (b) a regression in feel |
| 3. ProseMirror-family WYSIWYG (Tiptap, Milkdown) with a "lossless" round trip | Fails goal 1 structurally: no shipped lossless serialiser exists (GitLab's unfinished since 2022, Milkdown doubling backslashes in 2026-04, Tiptap's official extension "early release"). An outside change is a document replace that loses the cursor. Claude's edits must be re-parsed into the model | Best: syntax never shows; the legacy feel | Writes the serialiser's dialect over untouched text (list markers, escapes, entities): breaks DL-17's "never convert" and the Obsidian rule | Removes classes 3 and 4 (geometry, reveal). | 4. On option 3's premise. A document-model editor avoids legacy's problems only with a concrete-syntax tree that keeps every untouched node's original bytes and re-emits them verbatim, serialising only edited nodes. That is what GitLab's `preserve_unchanged_markdown` work attempts, and it has not landed in four years. Building it for Duo would be a research project on top of a rewrite, to win back a feel that Obsidian's users accept every day.

On option 4's timing. The stack recommendation already names a native editor as the tracked successor. Nothing in the field has changed that since 2026-10-03 except Lettera, which chose TextKit 1 and is a product, not a library. The trigger to revisit is a native rendered-markdown library with tables, virtualisation and a maintainer, not a date.

## What to do: keep the engine, close four bug classes at the root

The editor feels buggy for four reasons, and none of them is CodeMirror. Each has a small root fix and a check that keeps it closed. Together they are about two weeks of Sonnet sessions, in the order below, before any new editor feature (image paste, wikilinks, a calmer reveal) is built on top.

| Step | What it fixes | The root fix | The check that keeps it closed | Cost |
|---|---|---|---|---|
| 1. A geometry rule for block widgets | Class 3: clicks and selection landing lines away (C-25, F-249, F-251, and the three latent widgets proven today: image, deletion marker, table bar) | A block widget's root never carries an outer margin: `display: flow-root` and padding only, so CodeMirror's height map measures what is drawn. Three CSS rules today (`.duo-figure`, `.duo-deleted-block`, `.duo-table-bar`) | Extend `scripts/check-editor-selection.mjs` with a document that has every widget kind (image, deletion, table bar, properties block, rule, code fence) and assert zero height-map drift; run it in WebKit too (Playwright's WebKit build), since every check so far ran in Chromium | 1 to 2 days |
| 2.
