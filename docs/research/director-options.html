A director agent: the options, thought through

5 October 2026 · Follows docs/research/director-agent.md. Home Mac: Claude Code 2.1.289. Work Mac: 2.1.219.

Where I land: try the director at home this week as a skill, with no app code. At the same time, ask whether the work Mac can be updated. Write the director so that "tell a worker" and "hear back from a worker" are swappable. Then the work Mac's answer only decides which plumbing it uses, not whether the idea works. Build anything in Duo only if the home trial earns it and the work Mac can't be updated.

1 · Start from what a director actually does

Strip Claude Code Projects down and a director needs only four abilities. Everything else (the ledger, the review gate, merging with your go-ahead) is the director's own behaviour and works on any version.

On 2.1.219, verbs 1 and 2 work (claude --bg makes the worktree, claude agents --json shows state). Verb 3 is missing. Verb 4 half-works: a hook can write the worker's last message to a file, but nothing wakes the director by itself.

That reframes the work-Mac problem. It isn't "the work Mac can't run a director". It's "the work Mac is missing one wire and half of another." So the options are really different ways to supply those two wires.

2 · The options

Works at work: if IT allows

A · Update the work Mac

claude update to ≥ 2.1.236 (stable is 2.1.285). Both wires appear natively: SendMessage starts a turn in an idle worker, and notify_when_idle pings the director.

  • No code. The same director runs at home and at work.
  • Also brings the 2.1.222 fix: worktree sessions can no longer run destructive git on your main checkout.
  • Out of your hands if IT pins the version.
Works at work: no

B · Try it at home first, natively

A director skill plus agent definition. It uses duo2 session new to start workers, Duo tasks as the ledger, SendMessage to talk, and git to land. This is D0 from the research.

  • No app code. Running for real this week, on this repo.
  • Answers the question that matters most: does a director actually save you attention?
  • Doesn't help at work until A or D happens.
Works at work: clunky

C · Files and hooks only

Workers' Stop hooks write reports to .director/reports/, and Monitor wakes the director. To reach a worker, the director drops a note in .director/inbox/<id>.md, which a Stop hook hands over when that worker next finishes a turn.

  • Plain Claude Code. Works on 2.1.219, inside Duo or not.
  • An idle worker never sees its inbox. You must stop it and run claude -p --resume, which is ugly in a visible Duo terminal.
  • Hooks in every worker's settings. More moving parts to debug at work.
Works at work: yes, in Duo

D · Duo carries the messages

Two new duo2 verbs. duo2 message <session> "…" waits until the session's prompt is idle, then pastes the text and presses Enter. duo2 wait <session> returns when that session goes idle, with its last message.

  • Works on any Claude version Duo supports. Duo already does both halves: it types /cd + Enter into moved sessions (DL-64, AppModel.swift:330), and it already captures each turn's last message from the Stop hook (HookEvents.swift:95). DL-45 allows typing into sessions.
  • Everything stays visible in Duo's terminals. You can watch a worker get its instructions.
  • Typed text counts as you. A native SendMessage arrives marked as from another session, and can't approve anything. Text Duo types is indistinguishable from your own typing. See §4.
  • App code, after v1. Typing into a TUI is fragile if you're typing in that session at the same moment, or if a dialog is open.
Works at work: one task only

E · Agent teams

Experimental on 2.1.219 (CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1). It has a lead, teammates, a shared task list and mailboxes.

  • Real messaging between agents, today, at work.
  • The team lives and dies with one session and one task, so it isn't a director you keep feeding. No worktrees for teammates; they share a checkout. Token-heavy. Off by default, and IT may block the flag.
  • Still useful inside one worker, for a big refactor.
Works at work: yes, invisibly

F · Headless turns (a script runs the workers)

Each worker turn is claude -p --resume <id> "…" --output-format json. The result is the report, and the next instruction is the next turn. The director (or a script) runs them in the background.

  • Rock-solid on any version, including the old ones. No messaging needed at all.
  • Workers aren't live sessions you can glance at or step into mid-turn. Approvals can't be asked, so permissions must be set up front. It feels like a batch system, not a team.

4 · How I weighed them

Thought 1
The scarce thing is evidence, not plumbing. We don't yet know whether a director saves you attention or just moves it. Projects' early users report coordinators that relay rather than check (#97924), and plans drained "before lunch". The cheapest way to find out is B. It costs a skill file and runs where the plumbing is already complete. Nothing else should be built before that answer exists.

Thought 2
Don't pick the work-Mac plumbing yet; make it swappable. The director's skill only ever does two transport things: tell worker X and wait for worker X's report. If the skill says "use SendMessage if /list-agents exists, otherwise duo2 message if Duo offers it, otherwise the inbox file", the same director runs at home, at work after an update, and at work without one. That makes A, C and D interchangeable back-ends rather than competing plans.

Thought 3
A beats everything for work, if it's available. It's free and it's the version Anthropic tests. It also closes a safety gap that matters precisely for directors. Below 2.1.222, a worker "isolated" in a worktree can still run git reset --hard against your main checkout. So ask first.

Thought 4
If the update is refused, D is the better fallback than C. C's weak spot (an idle worker can't be reached) is exactly D's strength. D also fits Duo's direction: every action has a duo2 verb (DL-71), and Duo already types into sessions when that's simplest (DL-45). But D has one real cost, below, so it needs your decision, not mine.

The catch with D: whose voice is it? Claude Code deliberately marks cross-session messages as not from you. They "can't approve anything", and a worker treats them as a colleague's request. Text that Duo types into a terminal arrives as if you typed it. A director could then, in effect, say "yes, force-push" in your voice.

Mitigations:
  • Duo prefixes every typed message with [from director · not Geoff], and the workers' brief says such text never counts as your approval.
  • The workers' PreToolUse hook hard-blocks merges, force-pushes and destructive git whatever anyone says.
  • Duo refuses to type while a permission dialog is open.
That makes D acceptable, but it's still weaker than the native channel. It's the main reason D is a fallback, not the plan.

Thought 5
E and F aren't directors, but they're good tools for one. A worker can run an agent team or a workflow for a big task. A nightly sweep can be headless turns. Neither replaces the long-lived conversation you feed.

Recommended sequence
