The problem

You asked for this on 29 October:

"a user can open a Google Doc in Duo and view the document with nearly perfect rendering … use every single feature that Google Docs supports, including and especially low latency synchronous collaboration with other people … The user needs to be able to select text in the Google Doc and have Claude be aware of what text is selected. Claude needs to be able to go in and directly manipulate the Google Doc with tracked changes."

That's two sets of needs pulling in different directions.

  • You and your colleagues need Google's editor itself. Live typing, cursors, comments, version history, sharing and the hundred small features Docs has only exist in the real thing, and remote people are using the real thing in Chrome.
  • Claude needs a sharp, fast view of the doc and a way to change it. It has to know exactly what text you've selected, and its edits have to arrive as tracked changes (Docs calls them suggestions) that you and everyone else can accept or reject.

Google's editor draws the page on a canvas, so the text isn't sitting in the page where a script could read it. And Google's API (the official way for programs to read and change Docs) has no idea what you've selected. Each side is easy alone. The work is getting both at once.

Three ways to build it

You named the first two. The third is a mix that came out of the research.

A

Docs in Duo's browser

You + teamGoogle's editor in a Duo tab
Claudereads your tab, types in a hidden second tab
the live Google Doc

Real Docs for people, nothing to set up. Claude's edits are typed into your own session, which is less exact, and they stop when Duo is closed.

B

Duo's own editor, synced by API

YouDuo's copy of the doc
TeamGoogle's editor, in Chrome
ClaudeDuo's copy
synced to the Doc by API, seconds to minutes late

Full control for Claude, but you'd lose live collaboration and Docs' own look. Out, on your terms.

C · recommended

A, plus one tap for Google's API

You + teamGoogle's editor in a Duo tab
Claude readsyour selection, from that tab
Claude writessuggestions + comments by API, once you tap Allow
the live Google Doc

Everything A does, with no setup. One "Allow" per doc adds exact suggestions and comments, and lets Claude answer comments while Duo is closed.

How Claude gets API access, without setup work

Nobody sets anything up. Duo registers with Google once, as any app does, and each person just answers one "Allow" when they first need it:

  1. The first time Claude goes to suggest in a Doc, Duo asks: "Let Claude suggest edits and comment in this doc?"
  2. Google's own picker and consent appear inside Duo, through Google's sign-in kit for Mac apps (not Duo's browser tab, which Google refuses for this). If you're signed in to Google, that's one tap.
  3. Access covers only the Docs you allow, one at a time. Google calls this permission drive.file and classes it as non-sensitive, so Duo needs only Google's basic app check (a homepage, a privacy policy, a verified domain), not a security audit.
  4. Duo keeps the key in your Mac's Keychain and refreshes it quietly. It doesn't expire weekly; that only happens in Google's developer testing mode.

At work: Workspace's default lets people use any third-party app. Where an admin has tightened that, the person gets Google's "request access" button, and the admin approves Duo once for the whole company by its app id. Until then, that person still has everything in A, because the browser route only needs Docs to open in Duo.

Sources: Google's Drive scope guide (updated 3 Sep 2026), its OAuth guide for native apps (29 Oct 2026), and the Workspace admin help on app access (26 Oct 2026). What isn't proved yet: that Google's picker can grant a doc the person already has open in Duo in one step, and how long Google's basic app check takes. Phase 2 checks both.

What we know, and how we know it

Nothing has run in your Google account yet. Every test so far was signed out, on public Docs anyone can view, in Duo's browser engine (WebKit, Safari's engine) on the Mac mini. Signing in, editing and live collaboration are all Phase 2.

Two sessions did Phase 1 on 29 October. gdocs-landscape surveyed how other agents drive Google Docs. gdocs-frame (this one) took Duo's browser apart, probed a Doc and wrote the plan. Each fact below is tagged with how we know it.

Tested we ran it and measured it. Read it's in Google's own docs or in other projects' code. Inferred it's our reasoning or a second-hand report.

Tested here

These ran on a test copy of Duo (its own folders, never your Duo) and on a bare WebKit view set up the way Duo's browser tab is. The Doc was a public Chromium design doc: 5,104 characters, with headings, nested lists and 22 links.

  • TestedDocs loads and looks right in Duo's browser engine. There's no "unsupported browser" banner, and the page matches Chrome's. Duo's right pane is the problem: at 459 points wide, Docs' outline and a "Use Google Docs in Chrome" promo cover the page. F-411
  • TestedDuo's agent tools read none of a Doc today. duo2 browser read returns Docs' menus and the outline's headings, no body text. Scrolling and full-page screenshots see one screen, typing with fill can't reach the editor, and printing makes a PDF of pictures with no text. F-411
  • TestedDocs hands any script in the page its whole text and your selection. Docs' own page code has a function, _docs_annotate_getAnnotatedText, that it built for accessibility tools. Called from the page, it gave:
    • the whole document as text, in under 1 ms, including parts never scrolled to
    • every link and where it sits
    • the selection as character positions, which followed a real mouse drag and real Shift+arrow keys
    • a way to set the selection, which drew a real highlight on the page
    It didn't ask for an extension id or any setup, and it was ready about half a second after the page loaded. F-412
  • TestedReal mouse and key events drive Docs' editor with Duo in the background. A drag selected text and Shift+arrows extended it, from an app that never came to the front. So new duo2 verbs for keys and drags would work. F-413
  • TestedNo test copy of Duo can stay signed in. Test copies keep cookies only until they quit, and your Duo's cookies are shared by every Duo on this Mac. A test instance you sign into once needs a small change first. F-411, Q-312
  • TestedOther people's presence shows signed out. The viewers list read "7 total viewers: Anonymous Camel, …", so Docs' live channel runs in Duo's browser. F-411

Read in Google's docs or others' code

  • ReadSince 30 September, Google's API can write real suggestions and anchored comments. Edits sent in "suggest" mode show up as Docs suggestions anyone can accept or reject. Comments can be pinned to a passage and assigned to someone, and replies can resolve them. Before this, the API could only read suggestions. It covers personal accounts. I checked the announcement and Google's how-to page myself. F-409 · workspaceupdates.googleblog.com, 30 Sep 2026; developers.google.com/workspace/docs/api/how-tos/suggestions
  • ReadNothing official tells a program what you've selected, except a script installed in the doc itself (an Apps Script add-on), and that has to keep asking, since Docs has no "selection changed" event. Anthropic's own Claude add-on for Docs works this way. developers.google.com/apps-script
  • ReadGoogle offers no live feed of other people's edits. The old Realtime API was shut down in January 2019. Today's change notices say only "this file changed", with no detail, so a Duo-drawn editor would always lag. Drive push notifications; Workspace Events API
  • ReadGoogle's policy discourages signing in inside an app's built-in browser. Google's sign-in help says it "may" stop browsers "embedded in a different application", and its OAuth sign-in (the "let this app access your account" flow) refuses them outright. Duo's tab is such a browser. support.google.com/accounts/answer/7675428; Google developers blog, 2021
  • ReadSafari is a supported browser for Docs, except offline, which needs Chrome or Edge. Workspace supported browsers, Oct 2026
  • ReadOther tools use the same page function. Chromium's Reading Mode and the Harper grammar checker read text and the selection through it, and Harper edits by setting the selection and pasting. Browser agents (Claude in Chrome, ChatGPT's agent and others) have nothing special for Docs, and they work from screenshots. agent-landscape.md, F-410

Inferred

  • InferredThe page function is unofficial and could change without notice. Google documents none of it. Other sources describe it as gated by an allowlist of extension ids. It wasn't gated in our test, but it might be when signed in, in an editable doc, or later.
  • InferredClaude's suggestions will carry your name either way: from a hidden tab they're made in your session, and through the API they're made with your permission. Phase 2 checks what collaborators see.
  • InferredA hidden second tab can suggest without disturbing yours. Docs treats each tab as its own session, with its own caret and Suggesting switch. Untested.
  • InferredGoogle's picker can grant a doc you already have open in one tap. The picker can be pointed at a given file, but nobody has tried it from Duo.
  • InferredSign-in in Duo's tab may work, or may hit a "this browser may not be secure" wall. Enforcement varies by account. A managed work account may also insist on Chrome.
  • InferredA Duo-drawn editor (B) can't match Docs' live collaboration or look at any sensible cost. It would mean rebuilding Docs' layout, tables, chips, comments and sync, against an API that has no live edits and no cursors.

What it means

  • B is out. It fails the two things you named first, near-perfect rendering and live collaboration. Its one advantage was full control over Claude's edits, and Google's new suggest mode now gives that to the browser approaches too.
  • C is A with an upgrade, not a different product. Everyone gets A with no setup: Docs in Duo's tab, Claude reading your selection, and Claude suggesting from a hidden second tab in your own session. Where Google access is allowed, one tap per doc moves Claude's edits to the API. They become exact, they merge cleanly with live typing, they never touch your tab, and they work while Duo is closed (an @claude comment can be answered from a background session).
  • The setup cost lands on us, once. Duo registers its Google app and passes Google's basic check. Users never see Google Cloud. Work admins approve Duo once, or not at all if they leave the default.
  • The page function does the live work. It tells Claude your selection, and in the hidden tab it lets Claude select exactly the passage to change. If Google closes it, Duo keeps editing through the API where access is allowed, and falls back to Docs' own find and keyboard elsewhere.
  • duo2 needs new verbs either way:
    • a Docs read (text, links, selection)
    • keys and typing
    • drags
    • scrolling Docs' own scroller
    • export downloads
    • a test copy of Duo that stays signed in
    Duo's own shortcuts also collide with some of Docs': ⇧⌘H is Home in Duo and find and replace in Docs, ⌥⌘0 is collapse pane and Normal text, and ⌘P prints a picture of the page.
  • The first gate is sign-in. If Google won't let you sign in inside Duo's tab, both A and C need another way in, and the plan changes before anything else is built.

What I recommend

Aim for C, built in layers. First A, for everyone: Google's editor in Duo's tab, Claude reading your selection, and Claude suggesting from a hidden tab. Then the one-tap Google access, for Claude's exact edits and comments. Phase 2 tests it in this order, cheapest and most decisive first:
