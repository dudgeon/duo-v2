Where the file format forces a difference
  • Who closed it, and when. A file's comment has only done or not (Word's done, PowerPoint's status). Markdown writes a closing line with a name and date. For a thread Duo closes, Duo remembers who and when in its own state; for one closed in Word it shows “Closed” with no name. A reply to a closed thread reopens it (Word clears done on the root).
  • Delete and ⌘Z. Delete removes the comment, its replies and its anchor from the file's comment parts. ⌘Z restores them from the backup kept before the write (DL-331), so the file returns exactly; Markdown undoes through the editor's buffer.
  • Closed-thread look. Markdown's dotted anchor underline needs an anchor: a PowerPoint comment is on the whole slide, so its “anchor” is the slide's number marker, drawn dotted; a Word comment with no range (a point comment) has none either, and its folded line carries the dotted marker.
  • Suggestions. No suggestions of Duo's in a .docx or .pptx (a .docx's tracked changes stay as drawn, read only), so no Suggest Edits switch; the bar holds ‹ › and the Markup menu.
  • The bar at 460 (Word). ‹ › need room: Convert to Markdown… and Open With fold into ⋯ ⌄, as the Decks bar folds (DL-305).
  • Slides at a 460 pane. The rule is Markdown's: text (here the slide) takes what the margin leaves, 228 at 460. I drew the slide at normal size with the margin at 640 (S1, S2) and the gutter at 400 (S1b), and did not draw a 228 slide. Say if 460 should show something else.
  • Legacy PowerPoint comments are read only: cards with no highlight, reply field, Close or Delete.
PowerPoint anchors: what the format allows, what writing costs changed
  • The format (MS-PPTX, MS-ODRAWXML): a modern comment is anchored to the slide (pc:sldMkLst), a shape (ac:deMkLst with ac:spMk, picMk, graphicFrameMk…) or a character range in a shape (ac:txMkLst with ac:txMk cp and len). Google and LibreOffice: LibreOffice drops modern comments; Google's import is untested (C-179).
  • Reading all three anchors is cheap and is built first: the shape's id and name, and the text range, so the margin can draw the highlight and outline.
  • Writing a shape anchor needs the shape's id and its a16:creationId GUID (added to the slide's shape if it has none: that touches the slide part), and the slide's p14:creationId. In reach.
  • Writing a text anchor adds the character range, which PowerPoint re-finds by an ac:context hash I can't verify without a PowerPoint-written sample [unverified]. changed So 0.2.28 falls back: a comment “on a run of text” is written on its shape, and the verb says so. A range written by PowerPoint is still read and highlighted. Writing ranges waits for a sample.
  • changed Legacy comments: a slide that has them takes no new modern comment (it would renumber them); the verb says to comment elsewhere or open the deck in PowerPoint once to convert them.
  • Keeping anchors valid when the deck changes elsewhere: a shape id can change on copy, a range drifts when the text is edited. Duo never rewrites an anchor on its own. When it can't find one it shows the card with no highlight, as Markdown does for a comment whose text is gone.
  • A comment is on a slide, a shape or a run of text: “a comment on one shape” is no longer Not built.
