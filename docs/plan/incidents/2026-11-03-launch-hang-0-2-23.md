# Incident review: Duo 0.2.23 bounced in the Dock and never opened (2026-11-03)

One user's Duo 0.2.23 bounced in the Dock forever when opened from /Applications. Run from a terminal, it started and then crashed a while later. 0.2.22 had worked for them. Records: F-564, F-573, F-578 to F-580, C-157, C-159, ENH-324.

## What happened, and the cause

**The mechanism (reproduced).** `DuoApp.init` asked `ClaudeLocator.resolve()` for the `claude` path before the app had finished launching:
- The call is at `Sources/Duo/DuoApp.swift:82` (v0.2.23).
- When `claude` isn't at `~/.local/bin`, `~/.claude/local`, `/opt/homebrew/bin` or `/usr/local/bin`, `lookUp()` (`Sources/DuoKit/Terminal/Terminals.swift:35-53`, v0.2.23) runs `/bin/zsh -lc 'command -v claude'`. It then calls `waitUntilExit()` (line 50) and `readDataToEndOfFile()` (line 51). There is no time limit, and stdin is inherited.
- If the user's login shell doesn't end, Duo never finishes launching, and the Dock icon bounces for as long as the shell waits. Reasons a shell might not end: a `.zprofile` that waits on a prompt, a keychain, or a version manager, or a child that holds the pipe.

Run here against the notarized 0.2.23 and 0.2.22 DMGs:
- The setup: isolated, with `claude` hidden from the four places and a `.zprofile` that waits.
- Both hang the same way. `sample` shows `DuoApp.init → ClaudeLocator.resolve → lookUp → -[NSTask waitUntilExit] → CFRunLoopRun`, before `NSApplicationMain`.
- Neither writes a line to the hang log.

**Why the log was empty.** `waitUntilExit()` spins a nested main run loop until the task ends. That run loop drains the main dispatch queue, so HangMonitor's pings were answered every 50 ms, and nothing counted as a stall (F-573). The empty log was evidence for this cause, not against it.

**Why a terminal launch got further.** There the login shell has a terminal and the user's own environment, and answers.

### Why 0.2.23 and not 0.2.22 (F-578)

Duo's code didn't change here: this is not a code regression.
- The probe and its call site are the same in 0.2.22 and 0.2.23. They have been in every release since 0.2.0.
- Under the same trigger, 0.2.22's release binary hangs exactly like 0.2.23's.
- The two bundles have the same Info.plist keys, entitlements, Hardened Runtime flags and team, and the same Sparkle 2.10.0 code (only the signatures differ). Both pass `spctl`, `stapler validate` and `codesign --verify --deep --strict`. The two appcast entries have the same shape.

Geoff's observation is right: a `claude` in an unusual place never hung Duo before. That alone doesn't hang it now either. With an ordinary shell the probe answers in about 0.1 s and Duo opens. The hang needs two things: no `claude` in the four places, and a login shell that doesn't end when started the way Finder starts apps. So what changed with the update was most likely on the user's Mac, not in Duo: their shell's start-up, or where `claude` lives.

What I checked, and what's still open:
- **Claude Code moving its binary at the same time.** No entry in Claude Code's changelog from 2.1.310 to 2.1.318 moves the install or the launcher. On this Mac 2.1.316 is still at `~/.local/bin/claude` (a link into `~/.local/share/claude/versions`), and the npm copy is at `/opt/homebrew/bin/claude`. This doesn't rule out the user's own install changing (an npm or nvm install, a reinstall), which item 6 of the diagnostic asks about.
- **What only an update creates.** A leftover instance on the same support folder (the `second` case), and a dead instance's `endpoint.json` and socket (`stale-endpoint`), were run through LaunchServices on main's build (F-580) and on 0.2.23's code with the test hooks. They launch normally on both: nothing at launch talks to another Duo, and `ControlServer.start` unlinks a stale socket.
- **Migrations on the first launch after the update.** `state.json` decodes the same, with every key `decodeIfPresent`, so a Settings-chosen `claudePath` isn't lost. The new restore fields (`splits`, `splitRoom`) are optional, and the installer runs after launch. None of these can stop a launch.
- **Not reproduced: Sparkle's own relaunch, quarantine and App Translocation.** Sparkle strips quarantine, and the bounce happened on every later launch, not just the relaunch. A faithful run needs a visible launch under the real bundle id, so it waits on Geoff's OK.
- **A guess that fits all three facts, unconfirmed.** A `.zprofile` that touches something macOS guards (a protected folder, the keychain) prompts on behalf of the app that started the shell. From Finder that app is Duo, which may never have been asked, or was asked again. From a terminal it's the terminal, which already has the grant. C-159 tracks it until the user's answers come back.
- **"Crashes later from a terminal" is unexplained** (C-157). No crash site was found on the launch path of 0.2.23 or main.

## Why our testing missed it (F-579)

Every check that launched 0.2.23 skipped the probe, or ran it where it answers at once:
- **Release launch check** (`scripts/release.sh`, `launch_check`). It runs `--state overview --capture`, which is fixture mode, so `terminalsMode` isn't `.live`, and `DuoApp.swift:82`'s `if model.terminalsMode == .live` skips `resolve()` entirely. It proves the signed DMG draws a window, and nothing about a live launch.
- **Merge gate** (`scripts/merge-gate.sh`). DuoChecks tests the model and doesn't launch the app the way a user does. Its UI captures (check-ui, check-chat) are fixture states, and fixture states skip the probe as above.
- **Scale gate** (`scripts/check-scale.sh`). Live, but its stand-in `claude` is passed with `--claude`, so `resolve()` returns the chosen path before ever looking.
- **Background-launch check** (`scripts/check-background.sh`). It runs the fixture check set above.
- **Live runs on this Mac** (`run-live.sh`, the first worker's visible and upgrade runs). Here `claude` is at `~/.local/bin` and `/opt/homebrew/bin`, so `lookUp()` returns before the shell. They were launched from a terminal anyway, where the shell answers.
- **Field telemetry.** The hang monitor couldn't see a main thread stuck in a nested run loop. The one signal that should have pointed at the probe said the opposite, and the first worker took it at its word.

The pattern: every launch we test runs in this Mac's environment, and the probe's behaviour depends on the user's shell, which none of our checks modelled.

## Fixes

- **F-564** (merged 61e00310): the shell probe is bounded (3 s), stdin is `/dev/null`, and output is read as it comes. Launch resolves `claude` on a global queue, so the main thread never waits on the user's shell at launch. `DUO_CHECKS=launch-shell`.
- **F-573** (6716ae6c): HangMonitor watches the launch itself. Until `didFinishLaunching` calls `HangMonitor.shared.launchFinished()`, a launch past 10 s is sampled once a second, whether or not pings are answered. It writes `launching: not finished after N s` with the main thread's stacks every 10 s, and replaces it with `launching: finished after N s` if launch ends. `DUO_CHECKS=launch-hang` checks that, and scans `Sources/Duo` and `Sources/DuoKit` for any `waitUntilExit()` outside two reviewed off-main places.
- **F-580** (this commit): the release launch matrix, `scripts/check-launch-matrix.sh <app>`, run by `scripts/release.sh` on the signed app before notarizing.
  - **How it launches:** each case goes through LaunchServices the way Finder does (`open -g -n`, launchd's environment, stdin `/dev/null`).
  - **Isolation:** every case uses its own support folder and Claude config. Launches are background-only, so they never take focus.
  - **Pass rule:** each case must reach `didFinishLaunching` within 20 s. The app writes `Duo: finished launching in N s` from an isolated instance.
  - **Cases:** plain; `claude` missing from the four places (`DUO_CLAUDE_CANDIDATES`, honoured only by an isolated instance); that, plus a `.zprofile` that waits 40 s; one that leaves a child on the pipe; one that reads the terminal; PATH pointing nowhere; a dead instance's endpoint and socket; a second instance on the same folder.
  - **Proof it can fail:** the waiting-shell case also requires the "login shell didn't answer" line, so it can't pass by never asking the shell. On main all eight pass, each launch finishing in under 0.3 s. On 0.2.23's code with only the two test hooks added, the waiting-shell and child-on-the-pipe cases fail.

## Prevention and detection

1. **The launch matrix in every release** (F-580, built). A launch that depends on the user's environment is now tested the way users launch, in the environments we don't have. It runs before notarizing, so a failure costs a re-run, not a release.
2. **The launch watchdog** (F-573, built). If a launch ever hangs in the field again, `hangs.jsonl` has the stacks, and the diagnostic's item 5 (or `duo2 hangs --stacks`) brings them back.
3. **No blocking subprocess on the main thread** (F-573's scan, built). `DUO_CHECKS=launch-hang` fails on any new `waitUntilExit()` in app code. The two existing ones are listed with why they're off the main thread.
4. **Staged rollout** (ENH-324, proposed for Geoff):
   - Publish each release as a GitHub pre-release first. Sparkle's feed is `releases/latest/download/appcast.xml`, and `latest` skips pre-releases, so no user is offered it yet.
   - Geoff installs the DMG on both his Macs. The work Mac matters most: managed, a pinned Claude Code, the least like this one.
   - Soak at least 24 h of normal use on both, with at least three cold launches from the Dock each, and `duo2 hangs` showing no `launching:` line.
   - Then promote it to Latest (`gh release edit vX --latest --prerelease=false`), and Sparkle offers it.
   - Later: a Sparkle beta channel (`sparkle:channel`), with a Settings switch, for users who want builds first.
5. **Also worth adding** (in ENH-324):
   - A crash on the first launch after an update should come back to us. Duo could offer, on the next launch, to show the newest `DiagnosticReports` entry for Duo, so the user can send it.
   - The diagnostic page should ask for `duo2 hangs --stacks` first, now that it has something to say.
