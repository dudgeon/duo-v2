# Release test: the 0.2.25 candidate against 0.2.24 (2026-11-04)

**Verdict: hold 0.2.25.** One blocker: the GPU leak (C-161) is **not fixed**. In a busy isolated soak the candidate's GPU memory grew without a ceiling, to 3.5 GB in 55 minutes, no slower than 0.2.24 and probably faster (F-589, C-163). Everything else is clear, with the notes below.

Candidate: origin/main at `47ef3a5d` (the merge of fix/embedder-shapes; it contains the CPU refresh fix F-584 and the duo2 isolation guard F-529). Built with `scripts/bundle.sh release`. Baseline: the v0.2.24 release app, extracted from its DMG. Every run was isolated (`DUO_ISOLATED=1`, its own short `DUO_SUPPORT_DIR`, a scratch `CLAUDE_CONFIG_DIR`, a stand-in claude, project names that exist nowhere else), on the GPU lock (timed runs exclusive, through `timing-lock.sh` with `GPU_LOCK_MAX_MIN`). Raw outputs stay on the test machine (they hold machine data); this page has the numbers.

### The visible run (flows 1 and 2)

Run once with `DUO_TEST_FOREGROUND=1` (Geoff's OK by the director, 13:11–13:16, about 2.5 min per app, isolated, hard stop at 280 s per app, quit by SIGTERM). **It did not make the editor load.** The front app was `loginwindow` before and after every launch: the Mac's screen is locked, so a "visible" window can't be on screen. The result is the same as in the background, on both apps: `user-type: not found`, `disk-write: text not on disk`, `resolve: failed`, `bar-text text=""`; the file on disk stayed `Alpha line.` throughout; `duo2 doc status` says "not open in Duo"; SIGTERM quit in about 1 s and the harness quit in about 12 s on both. So **flows 1 and 2 of C-160 are still untested.** They need someone at an unlocked Mac, or Q-461's harness flag. Nothing the run did touched Geoff's Duo.

## Recommendations

1. **Hold 0.2.25** until the leak has a flat line: a 60 min soak with 0.2.24 as the control, and `EMBED_BATCHES=300` under a limit (say 700 MB), not just the 20-batch check.
2. The F-584 refresh fix is real (945 ms against 5.2 s) and the CPU is no worse (3d); it is not the whole story for large histories.
3. The first pass at C-161 measured the indexing model alone on short loops (F-585) and the fix was proven on 20 calls. A leak that is linear in calls needs a long-run check; `embedder-gpu` now takes one.

## How this was run

- Candidate: `scripts/bundle.sh release` at `47ef3a5d` (the shared lock). Baseline: `gh release download v0.2.24`, extracted from the DMG.
- Soak: `scripts/make-scale-fixture.py` (5 projects, 25 sessions) plus a writer that appends one user and one assistant turn to one session about every 8 s (each session once per ~200 s; the search service re-indexes a file 180 s after its last write, and releases the model after 180 s of no use, so a faster writer keeps files "waiting" and indexing idle: a first soak with a 12 s writer was discarded for that). `footprint` of the test pid every 60 s.
- Records: F-589 to F-592, Q-461, C-163; C-161 reopened.
- Runners: Haiku subagents ran the sweeps, menus, restores, captures, launch matrix, isolation, DuoChecks and flows; the soak, bench, CPU and idle runs and every verdict are the author's.
- Caveat: one early step ran 0.2.24 bare (`--version`), which starts the app on the real support folder; see F-590.

| Idle CPU, 6,150 sessions, 10 min, alternating in one hold | 101.3% and 102.8%; index passes 143 s (first) then 92–93 s | **119.6% and 123.0%** (first run on its own 120.2%); passes 275–294 s (first) then 148–154 s | **Regression: about 20 points more CPU, 60% slower passes.** The F-586 build had 81.6% and 93–94 s |

Cause of the idle-CPU gap (from a `sample` of the running build in a pass: 8 threads in Core ML model initialisation, `MLE5ProgramLibrary.lazyInitQueue`): `EmbedderSource.maxUses = 32` counts `get()` calls, one per small batch, and a bulk pass makes thousands of them, so the model reloads hundreds of times. A pass that embeds nothing neither loads nor releases the model, and the diff against `47ef3a5d` is only `Embedder.swift`, `SearchService.swift` and the bench. Bulk indexing (a first index, many changed files) pays it; the live soak does not. Sent to the director with a suggestion: budget the model's lifetime by work (chunks, or rows × length), not by calls.

**Verdict on `894df213`:** the leak fix is right; hold it for the bulk-pass cost. A new build needs the 6,150-session CPU (target: 93 s passes, CPU at or below 0.2.24), the 60 min soak and the 20 queries again, with 0.2.24 alternating in the same hold.

**Not tested live:**
- **A key, a click, and Duo becoming active, in the release app.** The test instance is a background accessory with no window shown. A key and a click posted to its pid (`CGEventPostToPid`) did not reach its event monitor ("NO POKE within 2 s"), and activating it would take focus (Geoff's OK needed). `DUO_CHECKS=backoff` sends a real key event through `NSApp.sendEvent` and posts the real activation notification, and passes. The visible gate would show the real path; it needs an unlocked Mac and Geoff's OK.
- **The needs-you notification itself.** Scripted runs set `DUO_AUTOCONFIRM`, which suppresses notifications (`notifyNeedsYou`), so only the pass is seen (`passCounts["notify"]` in the check). The live beacon test showed the poke and refresh but did not read the resulting needs-you count: `duo2 status` printed no matching line for my `grep`.
- **"The relative times catch up"** was not read off a screen either; the refresh returning to 2 s is the evidence.

**Side effect of a check:** `DUO_CHECKS=backoff` writes its beacon into the real `~/.claude/sessions` (the log shows `~/.claude/sessions/backoff-check-….json`) and removes it at once; none was left behind.
